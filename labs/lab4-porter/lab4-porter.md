# ЛР4. Пять сил Портера (адаптировано для e-business) + барьеры входа/выхода

Объект анализа: **DiagramCode** в границах рынка, зафиксированных в ЛР1 (русскоязычные IT-команды, инструменты «диаграмма как код» с AI-генерацией).

## 1. Матрица пяти сил

| Сила | Оценка (1/3/5) | Обоснование (с реальными данными) |
|---|---|---|
| Конкуренция между существующими игроками | **4 (высокая)** | Категория заполнена: PlantUML (открытый, встроен в IDE/CI, устойчивый рост интереса — ЛР1), Mermaid (открытый + коммерческий MermaidChart), D2, Eraser.io (венчурный стартап с AI и полноценным прайсингом — см. ЛР2-3). Прямых аналогов, совмещающих DSL + git-версионирование + AI + канвас + совместное редактирование в одном продукте, меньше (реально только Eraser.io делает похожий набор), но соседних ниш много |
| Угроза новых участников | **4 (высокая)** | Технический вход дешёвый (открытые парсер-генераторы, LLM API по подписке), особенно на фоне общего бума AI-инструментов для разработчиков. Реальный барьер — не технология, а доверие/сообщество/интеграции (GitHub, VS Code marketplace), которые у новых игроков нет с первого дня |
| Сила покупателей | **4 (высокая)** | Разработчики привыкли сравнивать инструменты и легко переключаются между бесплатными альтернативами (PlantUML/Mermaid — открытый исходный код, $0). Издержки переключения растут только после накопления истории версий и общего DSL-кода в DiagramCode — то есть сила покупателя высока именно до момента накопления данных |
| Сила поставщиков | **4 (высокая)** | Ключевая зависимость — внешний LLM/VLM-провайдер для AI-режимов (OpenAI/Anthropic и т.п.) и облачная инфраструктура (Neon Postgres, Render, Netlify). Частично снижено архитектурным решением: `AIProvider` — Strategy-паттерн за общим интерфейсом (`backend/app/domain/interfaces.py`), провайдер выбирается через конфигурацию `.env` без изменения кода — снижает, но не убирает зависимость |
| Угроза заменителей | **5 (очень высокая)** | Draw.io/Lucidchart/Visio (визуальные редакторы), Figma для схем, обычная текстовая документация без диаграмм вообще, ручное рисование на бумаге/доске — все это реальные заменители с нулевой стоимостью перехода для командыcommand, которая ещё не приняла привычку «диаграмма как код» |
| Цифровые усилители (сетевые эффекты/данные/платформы) | **3 (средняя)** | Сетевых эффектов пока мало (совместное редактирование — только Волна 2, ещё не реализовано); есть зависимость от алгоритмической видимости в поиске/GitHub для органического открытия продукта; данные пока не создают явного преимущества (нет накопленной обучающей выборки по AI-генерации) |

**Средневзвешенная оценка**: (4+4+4+4+5+3) / 6 ≈ **4,0 → высокое конкурентное давление**, на границе с «очень высоким».

## 2. Интерпретация по 2×2

Рынок «диаграмма как код» — это **высокая конкуренция + растущий спрос** (растущий спрос подтверждён в ЛР1 через тренд `text to diagram`). Согласно методике, это означает: рынок есть, но вход дорогой — нужно искать нишу, узкий сегмент и специализированное предложение, а не пытаться конкурировать по всему фронту сразу с PlantUML/Mermaid/Eraser.io.

**Практический вывод для DiagramCode**: не конкурировать с PlantUML/Mermaid за «бесплатный DSL-рендер» (там уже стандарт рынка, воспроизвести бесплатно несложно) и не конкурировать с Eraser.io напрямую по фиче-листу (у них есть финансирование и зрелый продукт) — а занять нишу **AI-генерация + git-подобное версионирование + весь набор инженерных нотаций (UML/ERD/IDEF/BPMN/сети Петри) в одном инструменте**, которую по отдельности не закрывает ни один из перечисленных конкурентов полностью.

## 3. Барьеры входа

| Барьер | Как проявляется для DiagramCode | Оценка |
|---|---|---|
| Технологический | Собственная грамматика DSL (Lark), рендер-движки, AI-интеграция — уже реализовано в архитектуре, умеренная сложность | Средний |
| Контентный | Нужна документация по DSL для каждой нотации (13 макетов интерфейса, cheat sheet синтаксиса) — объём есть в проекте, но требует поддержки | Средний |
| Доверительный | Ноль отзывов/кейсов на старте — придётся строить доверие с нуля против PlantUML с многолетней репутацией | Высокий |
| Канальный | Органика через GitHub/поиск (см. ЛР1: растущий тренд «text to diagram») — недорогой канал на старте | Низкий-средний |
| Правовой | Обработка пользовательского кода/диаграмм, GDPR-подобные требования при росте на СНГ+ЕС аудиторию | Средний |
| Операционный | AI-квота (20 запросов/день по умолчанию — уже заложено в архитектуре), нагрузка на воркер-пул при росте | Средний |
| Финансовый | Затраты на LLM API растут с базой пользователей — прямая зависимость от юнит-экономики AI-режимов | Высокий |

## 4. Барьеры выхода

| Барьер | Оценка для DiagramCode |
|---|---|
| Финансовые обязательства | Низкие — инфраструктура на условно-бесплатных тарифах (Render/Netlify/Neon), нет долгосрочных контрактов |
| Репутационные | Низкие на раннем этапе (мало пользователей = меньше репутационный риск при закрытии) |
| Техническая зависимость | Средняя — DSL-грамматика, парсер и модели переиспользуемы в других контекстах (открытая архитектура плагинов нотаций) |
| Данные пользователей | Средняя — версии диаграмм пользователей нужно будет либо экспортировать, либо гарантированно удалить при остановке проекта |
| Командная нагрузка | Низкая на этапе одного разработчика/курсовой работы |

**Вывод**: барьеры выхода низкие — решение о старте достаточно обратимо, что снижает риск эксперимента с запуском.

## 5. Итоговая формулировка

Адаптированный анализ пяти сил Портера показывает, что конкурентная среда рынка «диаграмма как код» определяется прежде всего высокой силой покупателей (лёгкость сравнения с бесплатными PlantUML/Mermaid) и очень высокой угрозой заменителей (визуальные редакторы, ручная работа). Наиболее значимым источником давления является не столько число прямых конкурентов, сколько доступность бесплатных альтернатив с нулевой стоимостью переключения. Привлекательность рынка оценивается как умеренная при условии узкой специализации: DiagramCode может закрепиться, если позиционируется не как «ещё один DSL-рендерер», а как единственный инструмент, сочетающий полный охват инженерных нотаций, git-подобное версионирование и AI-генерацию в одном продукте — то есть там, где сумма фич конкурентов по отдельности не закрывает потребность полностью.
