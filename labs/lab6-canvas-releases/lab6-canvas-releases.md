# ЛР6. Ценностное предложение, бизнес-модель Канвас, сценарии, страницы, релизы

Объект анализа: **DiagramCode**. Раздел опирается на уже принятые архитектурные решения реального продукта (`docs/architecture/`, `docs/requirements/` в основном репозитории продукта) — они не изобретены заново для этой лабораторной, а систематизированы в формате методики курса.

> **Исправлено после ревизии совета**: (1) в Канвасе «Потоки доходов» не было ни одной цифры — теперь явно указан $480/год из ЛР2-3; (2) пользовательские сценарии закрывали только одно из девяти требуемых методикой семейств («получение ценности») — добавлены сценарии монетизации, доверия, удержания и восстановления после ошибки, два из них — в полном 14-польном формате «паспорта сценария»; (3) страницы/экраны были просто списком из готовых макетов продукта, без связи со сценариями и без состояний интерфейса — добавлена матрица «сценарий → экран» и таблица состояний.

## 1. Ценностное предложение и цифровой товар

| Элемент | Значение |
|---|---|
| Целевой клиент | Команда разработки/техписатели, уже хранящая документацию в git (стартовый сегмент — ПВТ Беларусь, см. ЛР2-3) |
| Проблема | См. ЛР1/ЛР4/ЛР5: диаграммы либо теряют историю версий (визуальные редакторы), либо не имеют AI-генерации и полного охвата нотаций (существующие DSL-инструменты) |
| Результат | Мгновенная, версионируемая инженерная диаграмма из DSL-кода или из текста/изображения через AI, с полным охватом нотаций (UML, ERD, IDEF0/1X/3, DFD, BPMN, сети Петри) в одном инструменте |
| Механизм ценности | Реестр плагинов нотаций (`NotationProfile`) + парсер DSL (Lark) + AI-провайдер за общим интерфейсом (Strategy) + git-подобное версионирование (коммиты/блобы, дедупликация по SHA-256) |
| Отличие | Ни один прямой конкурент (ЛР5) не закрывает весь набор нотаций в одном продукте — DiagramCode целится именно в этот пробел |
| Доказательство | Растущий спрос на «text to diagram» (ЛР1), рыночный стандарт AI+версионирование+GitHub-интеграция уже подтверждён у Eraser.io (ЛР5) |

### Уровни цифрового товара (5-уровневая модель методики)

| Уровень | Состав для DiagramCode |
|---|---|
| Ядро пользы | Корректная диаграмма без ручной расстановки элементов — за секунды, из кода или из текста |
| Базовый товар (курсовой срез / Волна 1) | DSL-редактор (Monaco с подсветкой) + рендер + сохранение версий + нотация `erd.crows_foot.logical` с валидацией + аутентификация |
| Ожидаемый товар (рыночный стандарт, ЛР5) | Браузерный рендер без установки, интеграция с GitHub, AI-генерация, история версий |
| Расширенный товар (Волна 2-3) | Полный реестр нотаций (UML class/sequence/use case/activity/state machine, IDEF0/3, DFD), совместное редактирование в реальном времени через WebSocket, decomposition-модель для IDEF0/DFD |
| Потенциальный товар (Волна 4+) | BPMN всех видов, сети Петри с анализом достижимости для ограниченных сетей, экспорт в нативные форматы (PlantUML/Mermaid-текст, BPMN 2.0 XML, drawio-XML) |

### Единица монетизации

Подписка по местам с AI-квотой на тариф — та же модель, что подтверждена как рыночный стандарт у Eraser.io (ЛР5): бесплатный тариф с ограниченной AI-квотой (в архитектуре продукта уже заложено значение по умолчанию — 20 AI-запросов/день на пользователя через Redis-квоту), платные тарифы снимают ограничение.

## 2. Бизнес-модель по Канвас

| Блок Канвас | Содержание |
|---|---|
| Потребительские сегменты | Первичный: команды разработки/техписатели ПВТ Беларуси и СНГ. Вторичный: студенты и преподаватели курсов по моделированию (в том числе сам курс «ИТиВП» БГУИР — потенциальный образовательный канал). Третичный (после MVP): глобальный англоязычный рынок разработчиков |
| Ценностное предложение | См. раздел 1 |
| Каналы | Органический поиск (ключевые слова из ЛР1: «text to diagram», «diagram as code»), расширение/интеграция для GitHub (по аналогии с официальным расширением PlantUML — ЛР5), сообщества разработчиков, образовательный канал через вузы |
| Отношения с клиентами | Самообслуживание на бесплатном тарифе (документация, cheat sheet DSL — уже спроектированы как модальное окно документации), персональная поддержка на платных тарифах |
| Потоки доходов | Подписка по местам с AI-квотой на тариф: рабочее допущение **$8/участник/мес ≈ $480/год на платящую компанию** (5 человек в команде-адептере, обоснование и весь расчёт — ЛР2-3, раздел 4) — та же цифра, что использована во всех рыночных расчётах, без расхождений |
| Ключевые ресурсы | Грамматика DSL (`grammar.lark`), реестр плагинов нотаций, абстракция `AIProvider`, IDE-фронтенд на Monaco |
| Ключевые действия | Разработка новых нотаций по волнам (Wave 1-4), доработка промптов AI-режимов, поддержка рендер-пайплайна, поддержка документации |
| Партнёры | LLM/VLM-провайдер (OpenAI/Anthropic — сменный через `.env`), GitHub/GitLab (канал дистрибуции и интеграция хранения), Render + Netlify (хостинг), Neon (управляемый PostgreSQL) |
| Структура затрат | Переменные — оплата LLM API (растёт с базой пользователей, см. ЛР4 «сила поставщиков»); условно-постоянные — хостинг (бесплатные тарифы Render/Netlify/Neon на старте); разработка нотаций и AI-функциональности |

### Проверка связности

| Проверка | Результат |
|---|---|
| Сегмент ↔ ценность | ПВТ-командам, уже привыкшим к git-flow, ценность «диаграмма как код + версионирование» понятна без обучения |
| Ценность ↔ товар | Базовый товар (Волна 1: DSL+рендер+сохранение+`erd.crows_foot.logical`+auth) реально создаёт обещанную ценность для минимального сценария («написал DSL — увидел диаграмму — сохранил версию») |
| Товар ↔ доход | AI-квота как платный лимит — понятная точка монетизации, подтверждена рынком (Eraser.io) |
| Каналы ↔ рынок | Органика через GitHub/поиск соответствует поведению разработчиков (не требует холодных продаж) |
| Ресурсы ↔ релиз | Реестр нотаций уже архитектурно спроектирован как открытый для расширения (Open/Closed) — не требует переписывания ядра для новых нотаций по волнам |
| Затраты ↔ доход | Главный риск — рост затрат на LLM API быстрее роста платящей базы; квота 20 запросов/день по умолчанию — прямой инструмент контроля этого риска |

## 3. Бизнес-логика и пользовательские сценарии

### 3.1. Обзорная матрица по ролям (все 3 исходных сценария + 5 новых, закрывающих недостающие семейства методики)

| Роль | Цель роли | Основные сценарии | Ценность | Связь с монетизацией | Семейство (методика §9) |
|---|---|---|---|---|---|
| Посетитель (ещё не зарегистрирован) | Понять, подходит ли инструмент, прежде чем регистрироваться | Найти DiagramCode через поиск/GitHub → открыть лендинг/документацию → сравнить с PlantUML/Eraser.io | Снижение риска «зря потратить время на регистрацию» | Верхняя часть воронки — не платит, но конвертируется дальше | **Discovery / доверие-сравнение** (новое) |
| Новый пользователь после регистрации (первый запуск) | Получить первый успешный результат без чтения документации | Первый вход → IDE открывается в состоянии «Начальное» (см. §4.2) с подсказкой «Начните с шаблона или напишите DSL-код» → выбор шаблона нотации из панели (§4.1) → первый успешный рендер | Быстрый первый успех снижает отток на самом раннем шаге воронки, до того как пользователь вообще коснулся AI-режимов | Не платит на этом шаге, но от качества первого опыта зависит, дойдёт ли пользователь до точки монетизации вообще | **Онбординг/активация** (новое) |
| Пользователь (владелец диаграммы) | Написать/сгенерировать и сохранить диаграмму | Регистрация → вход → написание DSL → Run → сохранение версии → экспорт | Быстрый корректный результат без ручной расстановки фигур | Ядро продукта, бесплатный лимит | Ядро ценности |
| Пользователь как AI-заказчик | Получить DSL-код по описанию/изображению | Открыть модалку AI → выбрать режим (write/fix_code/fix_error/docs) → получить код → проверить на канвасе | Экономия времени на изучение синтаксиса DSL | Прямой источник расхода AI-квоты | Ядро ценности |
| Пользователь, исчерпавший AI-квоту | Продолжить пользоваться AI сверх бесплатного лимита | Получить уведомление об исчерпании квоты → увидеть тарифы → оплатить подписку | Непрерывность работы без потери прогресса | **Прямая точка монетизации** — паспорт ниже | **Монетизация** (новое) |
| Пользователь через месяц использования | Продолжать возвращаться к продукту | Открыть сохранённую диаграмму → увидеть историю версий → внести изменения | Накопленная ценность (история, привычка) удерживает от перехода к конкуренту | Снижает отток платящих мест | **Удержание** (новое) |
| Пользователь, столкнувшийся с ошибкой | Понять и исправить ошибку без потери работы | Ошибка синтаксиса DSL → вкладка Problems показывает строку/причину → режим AI «Исправить ошибку» предлагает фикс | Не потерять доверие к инструменту в момент неудачи | Косвенно снижает отток (плохой опыт ошибки = причина ухода) | **Поддержка/восстановление после ошибки** (новое) |
| Соавтор (Волна 2) | Совместно редактировать диаграмму | Получить приглашение → редактировать одновременно с владельцем → видеть изменения через WebSocket | Командная работа без конфликтов версий | Расширяет число платящих мест на одну диаграмму | Ядро ценности (командное) |

**Честная сверка с полным списком методики (§9, 9 семейств)**: закрыты 7 из 9 — discovery/доверие, **онбординг/активация** (добавлено при повторной доработке — использует уже спроектированные состояние «Начальное» и панель шаблонов, §4.1-4.2, без придумывания нового функционала), ядро ценности, монетизация, удержание, восстановление после ошибки, командная работа. **Не закрыты**: административные сценарии, партнёрские сценарии. Причина — не забывчивость, а честное отражение текущего состояния продукта: нет партнёрской программы и нет отдельной роли администратора, отличной от владельца, поэтому заполнять эти графы значило бы придумывать несуществующий функционал.

### 3.2. Паспорт сценария — «Оплата после исчерпания бесплатной AI-квоты» (полный формат, методика §10.1)

| Поле | Значение |
|---|---|
| Название | Переход на платный тариф после исчерпания AI-квоты |
| Роль | Пользователь (Free-тариф) |
| Контекст | Пользователь активно работает с AI-режимами несколько дней подряд |
| Триггер | Достигнут дневной лимит (20 AI-запросов/день по умолчанию) |
| Цель | Продолжить использовать AI без ожидания сброса лимита следующим днём |
| Проблема/барьер | Раздражение от блокировки в середине рабочей задачи; риск ухода к бесплатному конкуренту (PlantUML/Mermaid) |
| Предусловия | Пользователь зарегистрирован, у него есть хотя бы одна сохранённая диаграмма |
| Основные шаги | 1) Запрос к AI отклонён с объяснением причины → 2) Показан экран тарифов с прямым сравнением Free/платных лимитов → 3) Выбор тарифа → 4) Оплата → 5) Немедленное снятие ограничения |
| Данные | Текущее потребление квоты, история использования AI за период, выбранный тариф |
| Результат | Продолженная работа без потери контекста задачи |
| Точка монетизации | Именно здесь — единственный момент, где бесплатный пользователь превращается в платящего |
| Метрики | Доля пользователей, увидевших экран тарифов, которые оплачивают в течение 24 часов |
| Риски | Слишком агрессivnoe/непонятное сообщение об ограничении оттолкнёт, а не сконвертирует — формулировка ошибки требует отдельного UX-тестирования |
| Связь с Канвас | Напрямую реализует блок «Потоки доходов» (раздел 2) |

### 3.3. Паспорт сценария — «Восстановление после ошибки синтаксиса» (полный формат)

| Поле | Значение |
|---|---|
| Название | Диагностика и исправление ошибки DSL |
| Роль | Пользователь (любой тариф) |
| Контекст | Пользователь пишет или редактирует DSL-код вручную |
| Триггер | Парсер возвращает синтаксическую ошибку при нажатии Run |
| Цель | Получить корректный рендер, не разбираясь в грамматике DSL с нуля |
| Проблема/барьер | Сообщение об ошибке может быть непонятным новичку; риск бросить редактор в разочаровании |
| Предусловия | Есть текст DSL с ошибкой, доступна вкладка Problems |
| Основные шаги | 1) Ошибка подсвечивается в редакторе с точной позицией (строка/столбец) → 2) Вкладка Problems показывает текст ошибки → 3) Пользователь нажимает AI-режим «Исправить ошибку» → 4) Система передаёт AI код + текст ошибки → 5) Предложенный фикс встраивается в редактор с атрибуцией |
| Данные | Текст ошибки, позиция, исходный DSL-код |
| Результат | Работающий рендер без ручного дебага грамматики |
| Точка монетизации | Косвенная — расходует AI-квоту при использовании режима «Исправить ошибку» |
| Метрики | Доля ошибок, исправленных через AI-режим, vs. вручную |
| Риски | Если AI многократно предлагает неверный фикс — подрывает доверие к самому AI-режиму, не только к парсеру |
| Связь с Канвас | Снижает барьер входа (ЛР4, «доверительный барьер») за счёт быстрого восстановления после неудачи |

### 4.2. Состояния интерфейса (методика §12, 8 типов — ранее не описывались вообще)

| Состояние | Где проявляется | Что показывать |
|---|---|---|
| Начальное | IDE при первом открытии новой диаграммы | Пустой редактор с подсказкой «Начните с шаблона или напишите DSL-код» |
| Пустое | Список диаграмм пользователя без единой сохранённой версии | «У вас пока нет сохранённых диаграмм» + кнопка «Создать» |
| Загрузка | Рендер диаграммы, генерация AI-кода | Индикатор прогресса на канвасе / в модалке AI (AI-генерация может занимать секунды) |
| Ошибка | Синтаксическая ошибка DSL, сбой AI-запроса, исчерпание квоты | Точная позиция ошибки (строка/столбец) в редакторе; отдельное сообщение для AI-ошибок vs. синтаксических |
| Успех | Диаграмма успешно отрендерена, версия сохранена | Тост-уведомление «OK» (уже спроектировано, `.toast` в макетах) |
| Ограниченный доступ | AI-квота исчерпана (см. паспорт сценария 3.2) | Блокировка AI-кнопки + прямая ссылка на экран тарифов |
| Предупреждение | Валидация нашла warning, не блокирующий рендер (напр. ERD без первичного ключа) | Волнистое подчёркивание жёлтым в редакторе, вкладка Problems |
| Повторное использование | Возврат к ранее сохранённой диаграмме | Восстановление состояния канваса и позиции курсора из последней сессии |

## 5. Деление на релизы

Совпадает с уже принятой архитектурой реализации нотаций реального продукта (волны реализации) — не изобретается заново для курса, а используется как готовый, архитектурно обоснованный ответ.

| Релиз | Состав | Что проверяется |
|---|---|---|
| Первый релиз (курсовой срез / Волна 1) | DSL-редактор + рендер + сохранение версий + нотация `erd.crows_foot.logical` с валидацией + аутентификация + **экран тарифов/оплаты** (добавлен по итогам раздела 4 — без него точка монетизации нереализуема) | Спрос, готовность платить за базовый AI-режим, retention на минимальном сценарии |
| Второй релиз (Волна 2) | UML use case/sequence/activity/state machine, IDEF3, DFD с декомпозицией, совместное редактирование (WebSocket), режимы AI «Исправить код»/«Документация», OAuth-вход | Удержание, готовность команд к совместной работе, рост платящей базы за счёт мест на диаграмму |
| Третий релиз (Волна 3) | Остальные виды UML (13 канонических), IDEF1X отдельно от ERD, полные варианты ERD | Масштабирование охвата нотаций для более requirements-тяжёлых команд (аналитики, архитекторы) |
| Четвёртый релиз (Волна 4, после MVP) | BPMN всех видов, сети Петри с анализом достижимости для ограниченных сетей, экспорт в нативные форматы | Выход в смежные ниши (бизнес-процессы, формальный анализ) — отдельная волна монетизации для enterprise-сегмента |

### 5.1. Обоснование очерёдности (качественный скоринг, методика §8 — связь с ценностью/монетизацией/сложность/риск)

| Элемент | Связь с ценностью | Связь с монетизацией | Трудоёмкость | Риск отложить | Релиз |
|---|---|---|---|---|---|
| DSL-редактор + рендер + версии | Высокая — без этого нет продукта вообще | Косвенная | Низкая (уже реализовано) | Критический | Первый |
| Экран тарифов/оплаты | Средняя (не создаёт ценность сама по себе) | **Прямая, единственная точка монетизации** | Низкая | Высокий — без неё нельзя проверить готовность платить | Первый |
| Совместное редактирование (WebSocket) | Высокая для командного сценария | Косвенная (доп. места) | Высокая (требует синхронизации состояния) | Средний — можно проверить спрос и без этого в первом релизе | Второй |
| Полный охват нотаций (UML/IDEF/BPMN/сети Петри) | Высокая (ключевая дифференциация по ЛР5) | Косвенная | Очень высокая (годы разработки по волнам) | Низкий в моменте — дифференциация нужна для роста, не для проверки самой идеи | 2–4 |

## 6. Итог

Ценностное предложение, бизнес-модель, пользовательские сценарии, состав интерфейса и план релизов DiagramCode для целей этой лабораторной работы совпадают с реально принятыми архитектурными решениями продукта — курсовой анализ не придумывает альтернативную бизнес-логику, а формализует её в структуре, требуемой методикой курса «Электронный бизнес», подтверждая её рыночными данными из ЛР1-5.
