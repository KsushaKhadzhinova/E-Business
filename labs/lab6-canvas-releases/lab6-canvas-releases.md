# ЛР6. Ценностное предложение, бизнес-модель Канвас, сценарии, страницы, релизы

Объект анализа: **DiagramCode**. Раздел опирается на уже принятые архитектурные решения реального продукта (`docs/architecture/`, `docs/requirements/` в основном репозитории продукта) — они не изобретены заново для этой лабораторной, а систематизированы в формате методики курса.

## 1. Ценностное предложение и цифровой товар

| Элемент | Значение |
|---|---|
| Целевой клиент | Команда разработки/техписатели, уже хранящая документацию в git (стартовый сегмент — ПВТ Беларусь, см. ЛР2-3) |
| Проблема | См. ЛР1/ЛР4/ЛР5: диаграммы либо теряют историю версий (визуальные редакторы), либо не имеют AI-генерации и полного охвата нотаций (существующие DSL-инструменты) |
| Результат | Мгновенная, версионируемая инженерная диаграмма из DSL-кода или из текста/изображения через AI, с полным охватом нотаций (UML, ERD, IDEF0/1X/3, DFD, BPMN, сети Петри) в одном инструменте |
| Механизм ценности | Реестр плагинов нотаций (`NotationProfile`) + парсер DSL (Lark) + AI-провайдер за общим интерфейсом (Strategy) + git-подобное версионирование (коммиты/блобы, дедупликация по SHA-256) |
| Отличие | Ни один прямой конкурент (ЛР5) не закрывает весь набор нотаций в одном продукте — DiagramCode целится именно в этот пробел |
| Доказательство | Растущий спрос на «text to diagram» (ЛР1), рыночный стандарт AI+версионирование+GitHub-интеграция уже подтверждён у Eraser.io (ЛР5) |

### Уровни цифрового товара (5-уровневая модель методики)

| Уровень | Состав для DiagramCode |
|---|---|
| Ядро пользы | Корректная диаграмма без ручной расстановки элементов — за секунды, из кода или из текста |
| Базовый товар (курсовой срез / Волна 1) | DSL-редактор (Monaco с подсветкой) + рендер + сохранение версий + нотация `erd.crows_foot.logical` с валидацией + аутентификация |
| Ожидаемый товар (рыночный стандарт, ЛР5) | Браузерный рендер без установки, интеграция с GitHub, AI-генерация, история версий |
| Расширенный товар (Волна 2-3) | Полный реестр нотаций (UML class/sequence/use case/activity/state machine, IDEF0/3, DFD), совместное редактирование в реальном времени через WebSocket, decomposition-модель для IDEF0/DFD |
| Потенциальный товар (Волна 4+) | BPMN всех видов, сети Петри с анализом достижимости для ограниченных сетей, экспорт в нативные форматы (PlantUML/Mermaid-текст, BPMN 2.0 XML, drawio-XML) |

### Единица монетизации

Подписка по местам с AI-квотой на тариф — та же модель, что подтверждена как рыночный стандарт у Eraser.io (ЛР5): бесплатный тариф с ограниченной AI-квотой (в архитектуре продукта уже заложено значение по умолчанию — 20 AI-запросов/день на пользователя через Redis-квоту), платные тарифы снимают ограничение.

## 2. Бизнес-модель по Канвас

| Блок Канвас | Содержание |
|---|---|
| Потребительские сегменты | Первичный: команды разработки/техписатели ПВТ Беларуси и СНГ. Вторичный: студенты и преподаватели курсов по моделированию (в том числе сам курс «ИТиВП» БГУИР — потенциальный образовательный канал). Третичный (после MVP): глобальный англоязычный рынок разработчиков |
| Ценностное предложение | См. раздел 1 |
| Каналы | Органический поиск (ключевые слова из ЛР1: «text to diagram», «diagram as code»), расширение/интеграция для GitHub (по аналогии с официальным расширением PlantUML — ЛР5), сообщества разработчиков, образовательный канал через вузы |
| Отношения с клиентами | Самообслуживание на бесплатном тарифе (документация, cheat sheet DSL — уже спроектированы как модальное окно документации), персональная поддержка на платных тарифах |
| Потоки доходов | Подписка по местам с AI-квотой на тариф (см. раздел 1) |
| Ключевые ресурсы | Грамматика DSL (`grammar.lark`), реестр плагинов нотаций, абстракция `AIProvider`, IDE-фронтенд на Monaco |
| Ключевые действия | Разработка новых нотаций по волнам (Wave 1-4), доработка промптов AI-режимов, поддержка рендер-пайплайна, поддержка документации |
| Партнёры | LLM/VLM-провайдер (OpenAI/Anthropic — сменный через `.env`), GitHub/GitLab (канал дистрибуции и интеграция хранения), Render + Netlify (хостинг), Neon (управляемый PostgreSQL) |
| Структура затрат | Переменные — оплата LLM API (растёт с базой пользователей, см. ЛР4 «сила поставщиков»); условно-постоянные — хостинг (бесплатные тарифы Render/Netlify/Neon на старте); разработка нотаций и AI-функциональности |

### Проверка связности

| Проверка | Результат |
|---|---|
| Сегмент ↔ ценность | ПВТ-командам, уже привыкшим к git-flow, ценность «диаграмма как код + версионирование» понятна без обучения |
| Ценность ↔ товар | Базовый товар (Волна 1: DSL+рендер+сохранение+`erd.crows_foot.logical`+auth) реально создаёт обещанную ценность для минимального сценария («написал DSL — увидел диаграмму — сохранил версию») |
| Товар ↔ доход | AI-квота как платный лимит — понятная точка монетизации, подтверждена рынком (Eraser.io) |
| Каналы ↔ рынок | Органика через GitHub/поиск соответствует поведению разработчиков (не требует холодных продаж) |
| Ресурсы ↔ релиз | Реестр нотаций уже архитектурно спроектирован как открытый для расширения (Open/Closed) — не требует переписывания ядра для новых нотаций по волнам |
| Затраты ↔ доход | Главный риск — рост затрат на LLM API быстрее роста платящей базы; квота 20 запросов/день по умолчанию — прямой инструмент контроля этого риска |

## 3. Бизнес-логика и пользовательские сценарии

| Роль | Цель роли | Основные сценарии | Ценность | Связь с монетизацией |
|---|---|---|---|---|
| Пользователь (владелец диаграммы) | Написать/сгенерировать и сохранить диаграмму | Регистрация → вход → написание DSL → Run → сохранение версии → экспорт | Быстрый корректный результат без ручной расстановки фигур | Оплата за AI-квоту сверх бесплатного лимита |
| Пользователь как AI-заказчик | Получить DSL-код по описанию/изображению | Открыть модалку AI → выбрать режим (write/fix_code/fix_error/docs) → получить код → проверить на канвасе | Экономия времени на изучение синтаксиса DSL | Прямой источник платной AI-квоты |
| Соавтор (Волна 2) | Совместно редактировать диаграмму | Получить приглашение → редактировать одновременно с владельцем → видеть изменения через WebSocket | Командная работа без конфликтов версий | Расширяет число платящих мест на одну диаграмму |

## 5. Деление на релизы

Совпадает с уже принятой архитектурой реализации нотаций реального продукта (волны реализации) — не изобретается заново для курса, а используется как готовый, архитектурно обоснованный ответ.

| Релиз | Состав | Что проверяется |
|---|---|---|
| Первый релиз (курсовой срез / Волна 1) | DSL-редактор + рендер + сохранение версий + нотация `erd.crows_foot.logical` с валидацией + аутентификация | Спрос, готовность платить за базовый AI-режим, retention на минимальном сценарии |
| Второй релиз (Волна 2) | UML use case/sequence/activity/state machine, IDEF3, DFD с декомпозицией, совместное редактирование (WebSocket), режимы AI «Исправить код»/«Документация», OAuth-вход | Удержание, готовность команд к совместной работе, рост платящей базы за счёт мест на диаграмму |
| Третий релиз (Волна 3) | Остальные виды UML (13 канонических), IDEF1X отдельно от ERD, полные варианты ERD | Масштабирование охвата нотаций для более requirements-тяжёлых команд (аналитики, архитекторы) |
| Четвёртый релиз (Волна 4, после MVP) | BPMN всех видов, сети Петри с анализом достижимости для ограниченных сетей, экспорт в нативные форматы | Выход в смежные ниши (бизнес-процессы, формальный анализ) — отдельная волна монетизации для enterprise-сегмента |

## 6. Итог

Ценностное предложение, бизнес-модель, пользовательские сценарии, состав интерфейса и план релизов DiagramCode для целей этой лабораторной работы совпадают с реально принятыми архитектурными решениями продукта — курсовой анализ не придумывает альтернативную бизнес-логику, а формализует её в структуре, требуемой методикой курса «Электронный бизнес», подтверждая её рыночными данными из ЛР1-5.
